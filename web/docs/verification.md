# Local verification — 12 November 2026

The static app is built and verified locally at a repository subpath. No GitHub
repository, remote, push, workflow run, or publication was performed. All eight
Python source hashes still match the snapshot taken at the start of this port
([hashes](python-source-hashes.json)); the existing dirty Python working tree was
preserved.

## Browser and CLI throughput

The [browser spike](browser-throughput.md) used installed headless Chrome with
real cross-origin fetches. Mobile means iPhone 13 emulation at 390 CSS pixels,
150 ms latency, 1.6 Mbps down / 750 kbps up, and 4× CPU slowdown. It is not Safari
or physical cellular hardware. Fresh browser stores and `cache: no-store` exclude
local lookup/HTTP cache hits; upstream recursive caches remain uncontrolled.

| Measurement | Desktop | Mobile slow 4G |
| --- | ---: | ---: |
| RDAP-only, 240 fixed candidates | 16.012 s / 240 RDAP | 12.062 s / 240 RDAP |
| Split DoH gating, same 240 | 7.717 s / 112 RDAP | 6.156 s / 113 RDAP |
| RDAP-only sustained rate, latter half | 15.45 checks/s | 20.71 checks/s |
| Production worker, 200 available results | 18.646 s | 20.185 s |
| Production RDAP / DNS requests | 220 / 476 | 221 / 476 |
| Production RDAP requests skipped by DNS | 256 | 255 |

Verisign used HTTP/1.1 and no more than six on-wire requests at once. DoH used
HTTP/2 or HTTP/3; an additional QUIC-disabled run verified HTTP/2. Cloudflare's
throttled-mobile sweep plateaued at 24 DNS slots; 48 increased median latency
from 180 to 360 ms. Production uses 12 slots per provider, six RDAP slots,
independent budgets, a 250 ms idle-RDAP hedge, and a two-second DNS deadline.
No HTTP 429 appeared live; DNS SERVFAIL/timeouts did. Throttling and overload
recovery were tested with controlled providers, not inferred from that absence.

Both production runs returned exactly Python's first 200 available names in the
same order, and every available row had an RDAP source. These measurements use
the production worker, IndexedDB commits, bounded lookahead, pacing and retries;
the spike numbers omit those costs. [Production evidence](production-throughput.json).

The earlier [CLI measurements](../../docs/domain-lookup-dns.md) give context:
200 available names took 11.375 s RDAP-only (481 attempts); with DNS, the first
run took 22.966 s and the repeat fresh-cache trial 11.019 s. The CLI's 1,000-result
RDAP-only run achieved 93.5 attempts/s overall and 119.1/s after ramp-up using
32 workers. These are different runs and transport pools. The browser is
connection-limited; they do not establish a controlled browser/CLI speed ratio.
Sequential remote measurements also do not establish that mobile is faster.
No 4,000-result browser endurance benchmark was run.

### Interface redesign (12 November 2026)

The interface was redesigned to the standard set out in the [design brief](design-brief.md).
That brief comes from boat.dev, studied in Chrome at 1440 px and 390 px; references
are in [design-ref/](design-ref/). Generation, lookup, storage and worker code are
unchanged, and both worker bundles keep their content hashes. Every check above was
rerun after the redesign. The pre-redesign captures are kept as `*-before.png`.

- Comparisons: [390 px](screenshots/side-by-side-mobile.png) and
  [desktop](screenshots/side-by-side-desktop.png), each showing the boat.dev
  reference, before and after.
- At 390 px, nine full result rows sit above the fold, below the controls; the old
  layout showed none. At 1440 × 900, all 24 are visible.
- Deterministic state captures, made with mocked providers by
  `node scripts/design-screens.mjs`:
  - `initial`, `checking`, `results` (with `-full`), `folds-open`, `reverse`,
    `substitutions`, `shortlist` and `offline`;
  - each as `mobile-*.png` and `desktop-*.png` in [screenshots/](screenshots/).

The [controlled recovery verifier](resume-verification.json) uses mocked RDAP/DoH
with delayed early candidates. It pauses before completion, reloads/resumes,
compares two ordered filtered pages against the Python fixture, revisits a saved
page with **zero network calls**, verifies fresh-check bypass and offline/online
resume, and exercises original styles, restored 15-letter length limits, and
keyboard tabs. This verifies lifecycle handling in Chrome; it does not simulate
every physical iOS process-kill condition. Visibility handling is implemented,
but physical Safari suspension remains unverified.

## Bundle and load performance

Production build: **10,184 bytes gzip entry JS** (12,906 before the redesign),
5,214 bytes CSS; **28,492 bytes gzip for all JavaScript including both workers**
(previously 31,214). This is below the 100 KB JS target. The static app shell is
now HTML (`src/shell.ts`, injected at build time), and `index.html` is 3,758 bytes
gzip. There are zero runtime dependencies.

Three self-hosted OFL font subsets total 17,416 bytes of WOFF2 (`scripts/fonts.py`).
On a first visit they load only after the first results frame. Later visits enable
them before first paint. Metric-matched fallbacks keep the swap at CLS 0. The full
126,052-word compact CMU asset is 2,320,867 bytes raw / **816,962 bytes gzip**;
it is absent from initial-load requests and the shell precache. It loads only
when analysis needs it. [Build sizes](bundle-size.json).

Lighthouse mobile, on the gzip production preview under `/brand-name-explorer/`,
with default simulated mobile throttling: **LCP 0.752 s, TBT 0 ms, CLS 0**,
performance **100**, accessibility **100**. Before the redesign: LCP 0.943 s,
CLS 0, 100/100. The audited transfer is **38,916 bytes** (18,348 before); the
difference is mostly font subsets and the static HTML shell. That audit omits some worker/service-worker precache traffic; it is not
the entire installed offline shell. [Compact audit summary](lighthouse-mobile-summary.json). Full JSON/HTML reports
are generated locally by the reproduction command and are gitignored.

A separate installed-Chrome test records server-side compressed response bodies,
including workers and service-worker installation. It uses CDP slow 4G/4× CPU,
with generation enabled and no domain work. A cold load transfers about **63.2 KB**
for the whole installed shell, including the fonts and their licence. Repeat loads
need only the **856-byte service worker update check** in this test. The offline iteration stops its isolated
preview server as well as setting the browser context offline, and transfers
**zero bytes**. Browser resource timing alone undercounts service-worker traffic.
The exact observed timings and per-resource accounting are in
[load-measurements.json](load-measurements.json). These are local preview numbers,
not github.io measurements. Payload totals exclude HTTP headers.

| Load | Generator usable | Observed LCP | Observed TBT | Server compressed bodies |
| --- | ---: | ---: | ---: | ---: |
| Cold | 504 ms | 424 ms | 0 ms | 63,248 bytes |
| Repeat | 92 ms | 72 ms | 0 ms | 856 bytes |
| Offline, server stopped | 78 ms | 68 ms | 0 ms | 0 bytes |

Before the redesign these were 560 / 532 / 0 ms and 37,470 bytes (cold), 80 / 60 /
0 ms and 785 bytes (repeat), and 78 / 56 / 0 ms (offline). In three runs of the
same build, the repeat-load usable time varied between 92 and 113 ms. A build
without fonts measured 86 ms.

These direct wall-clock observations are separate from Lighthouse's simulated
metrics above; they use different measurement methods.

## Reproduce

Requires Node 22.12+ and installed Chrome. No Python runtime is needed for the app.

```bash
cd web
npm ci
npm test
npm run build
npm run preview:pages
# Leave the server running; another terminal from web/:
npm run test:resume
npm run test:browser
npm run benchmark:production
npm run measure:load
./node_modules/.bin/lighthouse http://127.0.0.1:4173/brand-name-explorer/ \
  --chrome-path='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' \
  --chrome-flags='--headless --no-sandbox' \
  --only-categories=performance,accessibility --output=json --output=html \
  --output-path=docs/lighthouse-mobile --quiet
```

Run performance measurements sequentially with other browser tests stopped.
`measure:load` starts its own gzip server on port 4174 and stops it for the
offline iteration. Browser scripts mostly support `CHROME_PATH`; the recovery,
load and HTTP/2 scripts currently use the macOS installed-Chrome path directly.
For the spike sweeps, follow [the separate reproduction commands](browser-throughput.md#reproduce-and-evidence).
`npm run fixtures` regenerates compact assets and parity data from Python.

## Remaining limits and next check

Physical iPhone/Safari testing and an actual GitHub Pages deployment remain
unverified. A Pages-like local subpath, gzip, 600-second caching, and absence of
COOP/COEP were verified. Modern browser APIs are required (approximately Safari
17.4+). Where Web Locks is unavailable, use one checking tab per origin.

Browser storage can be denied or evicted; persistence is requested, and portable
JSON shortlist backups are provided. Cache clearing preserves shortlist and
saved session pages. Large generation pages and replaying very late cursors can
take longer on a phone. Next: test Safari on a physical iPhone through tab
suspension/reload, then verify the scoped service worker on the eventual Pages
URL before treating deployment and mobile lifecycle behavior as established.
